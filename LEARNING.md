# LEARNING.md — what we built and why, phase by phase

## Phase 0: Setup

**What we built.** Folder layout, a virtual environment, `requirements.txt`, `.env.example`, `.gitignore`, a README with the CORD attribution, and `scripts/hello.py` which proves the API key works.

**Why it's designed this way.**
- The API key lives only in `.env`, which `.gitignore` blocks. Code reads it with `python-dotenv` and the Anthropic client picks it up from the environment, so the key never appears in source.
- `.env.example` is committed instead, so anyone cloning knows which variable to set.
- Default model is Claude Haiku 5.5 (`claude-haiku-5-5`): cheapest current model, supports images, so the full test set costs cents. Claude Opus 5.5 (`claude-opus-5-5`) is the larger model for the comparison in Phase 5.
- The hello script lists models from the API rather than hardcoding knowledge, so model IDs are checked against the account, not guessed.

**Likely interview questions.**
- *Why not just paste the key into the script?* Anything in a public repo is public forever, even if deleted later. Secrets go in environment variables; `.env` is a local convenience for that.
- *Why a small model by default?* Most of the pipeline's hard logic is in plain Python. The LLM only needs to read the image well, and we measure whether a small model is good enough before paying for a larger one.

**Trade-off.** Python 3.13 is installed rather than the 3.11/3.12 the brief suggests. All pinned libraries install on 3.13; if one breaks later we can switch the venv to 3.12.

## Phase 1: Data

**What we built.** `data/prepare.py` downloads CORD v2, saves the 200 validation and test images, and writes one clean JSON record per receipt to `data/gt/`. `src/receipted/parsing.py` holds the two string-to-number parsers, with 36 pytest cases. `data/train_item_names.txt` lists 1,482 item names from the train split for the synthetic price list in Phase 3.

**Why it's designed this way.**
- We surveyed every quantity and price pattern in the data before writing the parser, so the rules come from what is actually printed, not guesses. Prices appear as `16,500`, `16.500`, `35000.00`, `45,000.00`, `9.500,00` and `Rp 58000.00`; quantities as `1`, `x2`, `2 x`, `1Prs`, `1.00` and `*2`. The rule "a separator followed by 3 digits is a thousands separator; a final separator followed by 1 or 2 digits is a decimal point" covers all of them.
- Prices are stored as integers because Rupiah has no cents. Missing fields are `null`, never 0, so later checks can tell "not printed" from "printed as zero".
- The clean JSON is committed (small, and CC BY 4.0 allows it with credit); images are gitignored and regenerated by the script.
- Each record also carries `checks`: whether the ground truth itself adds up. About two-thirds of receipts print a subtotal; among those, roughly 1 in 10 does not add up cleanly. Reasons we found: tax-inclusive line prices (lines sum to the total, not the subtotal), per-item discounts that only appear on the item lines, rounding to the nearest thousand, and a few plain annotation mistakes.

**Why that last point matters.** Phase 3's maths check must accept "lines equal subtotal" *or* "lines equal total" (tax-inclusive) and must subtract item discounts, or it will raise false alarms on real receipts. Phase 5 should plant "totals don't add up" errors only on receipts whose ground truth is consistent, otherwise we can't tell a caught error from a receipt that was already broken.

**Likely interview questions.**
- *How did you handle messy number formats?* Looked at the real distribution first, wrote one small pure function with the two-rule heuristic, and unit-tested it against every pattern seen, including the list-valued fields CORD uses when a value is printed twice.
- *What surprised you in the data?* Ground truth is not perfect: a few item names are in a different word order from the receipt, about 10% of receipts with a subtotal don't add up, and 20% of images are larger than the model's 1568-pixel limit, which matters for Phase 2's upload size.

**Trade-off.** Sub-items (toppings, modifiers) are flattened into the item list with an `is_sub_item` flag rather than nested, because they carry their own price on the receipt and must count towards the subtotal.

## Phase 2: Extraction with the AI

**What we built.** `src/receipted/schemas.py` (the Pydantic shape of a receipt), `src/receipted/llm.py` (client, model names, prices, disk cache), `src/receipted/extract.py` (image prep, the API call, one retry, caching), and `scripts/compare_extraction.py` to eyeball extracted vs ground truth.

**How image input works.** The image file is read as bytes, base64-encoded, and sent as an `image` content block alongside the text instruction in one user message. The model sees pixels, not OCR text, so it can use layout (columns, alignment) the way a person does. We resize to a 1568-pixel long edge and JPEG-encode first: the API downsizes anything larger anyway, so sending a 4096-pixel photo only slows the upload. Cost is driven by pixel area; a typical receipt is about 1,500 to 3,000 input tokens.

**Why structured output plus validation.** We pass the Pydantic class to the API's structured-output mode, which constrains the model to emit JSON of exactly that shape, and Pydantic validates the reply on our side. Two layers: the schema stops free-text drift, the validator catches anything that still slips (wrong type, missing field). If validation fails we retry once with a nudge; if it fails again we raise `ExtractionError`, which the graph in Phase 4 will route to human review instead of guessing.

**Why caching.** Every call costs money and 2 to 5 seconds. The cache key is a hash of the resized image bytes, the prompt version, the system prompt text and the model name. Change any of those and you get a fresh call; change nothing and the re-run is free and reproducible. Each cache entry also stores token counts, latency and cost, so Phase 5 can report them without re-running.

**What the first 5 receipts showed.** Prompt v1 got every item and total right but listed unpriced modifier lines ("Less Ice", "70%") as items. Prompt v2 says lines with no price are modifiers and should be left out, and that fixed it. One remaining "difference" is a label problem, not a model error: CORD calls the "ITEMS: 1 41,000" line a subtotal, and skipped a printed "- Sedang 0" line that the model correctly extracted. Expect some of the measured error in Phase 5 to be label noise.

**Likely interview questions.**
- *Why not use a traditional OCR engine?* OCR gives you characters, not meaning; you'd still need to pair quantities, names and prices across columns on a crumpled photo. A multimodal model does both steps at once and returns typed fields. The trade-off is cost and latency per call, which caching and a small model keep low.
- *How do you know the model didn't make numbers up?* We tell it to report only printed values and use null otherwise, and Phase 3's maths checks and Phase 5's comparison against ground truth measure how often that holds. The `readability` field lets it declare uncertainty instead of guessing.

**Trade-off.** Effort is set to "medium" for both models so the small-vs-large comparison is fair. Lower effort would be cheaper and faster; we can test that on the validation split later.

## Phase 3: Checks — maths, price list, policy with RAG

**What we built.** `maths.py` (deterministic receipt and claim checks), `fixtures/policy.md` (13 synthetic clauses) and `fixtures/price_list.csv` (126 synthetic rows grounded in train-split prices, generated by `fixtures/make_price_list.py`), `retrieve.py` (Chroma store over clauses and price rows), `rules.py` (LLM rule check with structured output) and `verify.py` (the evidence verifier). 57 tests pass. `scripts/try_checks.py` runs the whole chain on three hand-made claims in `fixtures/sample_claims.json`.

**Why the maths is in code, not the LLM.** Language models predict text; they do not compute. They get long sums wrong often enough that you can't trust a verdict like "the lines add up". Python does arithmetic exactly, runs in microseconds, costs nothing, and gives the same answer every time. So every number comparison lives in `maths.py`, and the LLM receives the results as facts. The LLM only does what code can't: judging that "Bir Bintang" is beer, or that "Siomay Kombinasi" on the claim is the "Siomay Kmbinasi" on the receipt.

**Why a tolerance.** Real receipts round to the nearest thousand rupiah and print tax to the rupiah. Phase 1 showed about 1 in 10 receipts with a subtotal does not add up exactly, and that lines sometimes sum to the total rather than the subtotal when tax is included. The checks allow max(1 unit, 0.5%) and accept either target, which removes false alarms without hiding real errors (a planted error is far larger than 0.5%).

**What RAG adds here.** The policy and price list are embedded once into a local Chroma store. For each receipt item and for the claim as a whole we retrieve the nearest clauses and price rows and give only those to the LLM. Honest caveat: with 13 clauses you could paste the whole policy into the prompt. Retrieval is built the way it would have to be for a 40-page policy or a 5,000-row price list, where the prompt can't hold everything and irrelevant text degrades answers. It also gives the verifier an allowlist: a cited id must be one that actually exists.

**How the verifier stops hallucinated flags.** The rule check must cite a clause id or price-list item *and* the receipt line it applies to. The verifier, in plain Python, drops any issue whose clause id is not in `policy.md`, whose price item is not in the CSV, or whose receipt line does not match an extracted line (whitespace and case ignored). For price issues it re-does the comparison itself: the line's unit price must really be above the agreed maximum. A flag that can't point at real evidence is thrown away and counted, and Phase 5 reports how many were dropped. This is the "no evidence, no issue" rule from the Origgin story, in code.

**Why rules.py can still add value on top of maths.py.** When the maths finds an over-claim, the rule check attaches the policy clause (C4) that says what to do about it. Numbers from code, consequence from policy; Phase 4 merges the two into one issue for the reader.

**Likely interview questions.**
- *Why Chroma?* Local, persistent, free, and it bundles an embedding model, so the demo runs anywhere with no extra services. For a production system you'd evaluate hosted vector stores and a stronger embedding model; the retrieval interface would not change.
- *Could the model still cite a real clause for a wrong reason?* Yes. The verifier checks that evidence exists, not that the reasoning is right. That residual risk is what the Phase 5 false-alarm rate measures, and why medium-severity issues route to a human.

**Trade-off.** Whole-claim rules (approval thresholds, over-claims) have no single receipt line to cite, so two anchor tokens, `RECEIPT_TOTAL` and `CLAIM_AMOUNT`, are allowed as the cited line. It keeps the "every issue cites a line" rule honest without forcing the model to invent a line.

## Phase 4: The agent graph

**What we built.** `graph.py` wires the steps into a LangGraph state graph: extract → maths_check → retrieve → rule_check → verify → decide → draft, with one branch after extract. `draft.py` writes the message. `run.py` is the CLI (`python -m receipted.run --sample SAMPLE-002`). Every node is wrapped so the trace records its time, a one-line summary, and tokens and cost for the LLM nodes.

**What makes this "agentic".** The system is not one prompt that answers a question. It is a sequence of specialised steps, some of them model calls and some plain code, that share state, and a routing decision that depends on what an earlier step found: if the receipt can't be read, the checks are skipped and the claim goes to a human. The model's job at each step is narrow (read this image; apply these clauses to these lines; write this message), and code decides what happens next.

**Why a graph instead of one big prompt.**
- Each step can use the right tool: an image model for reading, Python for arithmetic, a vector store for lookup, a text model for writing.
- Each step can be tested and measured on its own. Phase 5 reports extraction accuracy separately from rule-check recall.
- The verifier sits *between* the rule check and the decision, so a hallucinated flag is removed before it can affect anything.
- A trace of every node's output and timing makes failures explainable: you can see which step went wrong and what it cost.
- Routing is explicit code (`route_after_extract`, `decide`), not something the model is trusted to do.

**The human-review route.** Three things send a claim to a person instead of an automatic answer: the extraction failed validation twice, the model declared the image unreadable, or no issues were found but the model said parts were hard to read. Verified with a blurred noise image: the graph went extract → decide → draft, no checks were run, and the draft asked for a clearer photo. Conservative by design: the cost of a wrong automatic approval is higher than the cost of a treasurer glancing at one more claim.

**Likely interview questions.**
- *Isn't LangGraph overkill for seven steps in a line?* For a straight line, yes, a loop of function calls would do. The value shows up with the branch, the shared typed state, the per-node trace, and the fact that adding a step (say, a duplicate-receipt check) is one node and one edge rather than a prompt rewrite.
- *What does the draft model know that the user doesn't?* Nothing. It only receives the verified issues with their evidence and the decision, and is told to add no facts. The LLM-as-judge in Phase 5 scores whether it stayed within that.

**Trade-off.** The maths check and the rule check can report the same problem twice, once with numbers and once with the clause. Rather than merge them with fragile matching code, the decision uses the maximum severity (so duplicates change nothing) and the draft prompt is told to present each distinct problem once. Simple, and the duplication stays visible in the trace for debugging.

## Phase 5: Evaluation

**What we built.** `eval/make_claims.py` (synthetic claims with planted errors and labels, fixed seed), `eval/eval_extraction.py` (extraction vs ground truth, per model), `eval/eval_checks.py` (the full agent on every claim, scored against the labels), `eval/eval_drafts.py` (LLM-as-judge with a written rubric, plus a sheet for human scoring and an agreement calculation), `eval/report.py` (metrics.json, results table, charts, failure fact sheet). All numbers in the README come from `results/`.

**How the claims were made, and what "caught" means.** Half the test claims are clean copies of the ground truth. Each of the rest gets exactly one planted error: inflated amount, wrong quantity, an extra item that is not on the receipt, claim lines that don't sum to the claimed amount, or a policy breach written into the claim (a meal for "1 person" above the per-person cap, or no purpose stated). Two breaches live in the receipt image, not the claim, so they can't be planted: a price above the agreed list and alcohol on the receipt. Those are labelled from ground truth wherever they occur naturally. Receipts whose own ground truth doesn't add up are labelled too, so a maths flag there counts as correct. An error is "caught" when a verified issue of the matching kind exists, not merely when the decision isn't approve. A false alarm is a clean claim with no natural breach that gets a verified issue. Clean claims held only because the model said the image was partly unclear are counted separately, because that is the human-review route working as designed, not a wrong flag.

**Why validation for tuning and test for the final number.** Every prompt change (two extraction prompt versions, three rule-check prompt versions, the judge's fact list) was made on 10 validation receipts. The test split was run once, after the prompts were frozen. If you tune on the data you report, the number measures how well you fit those 100 receipts, not how the system would do on the next 100.

**LLM-as-judge, and why a rubric and a human check.** A larger model (Opus 5.5) scores each Haiku-written draft 1 to 5 on accuracy, evidence, clarity and tone, using a written rubric that names what a 5, 3 and 1 look like. The judge is given exactly the facts the writer was given, so "the message mentions the claimed amount" is not an accuracy error. The first judge run scored accuracy 3.0 because it was *not* shown those facts; fixing the judge, not the drafts, took it to 4.9. That is the lesson: a judge is itself a prompt that can be wrong, so 10 drafts are scored by a person and the agreement is reported.

**Likely interview questions.**
- *How did you measure it, and why not test on the data you tuned on?* Three separate measurements (extraction accuracy, errors caught vs false alarms, draft quality), each with its own ground truth or labels. Tuning used the validation split; the test split was run once at the end.
- *What is the weakest part of the evaluation?* The claims, price list and policy are synthetic, so the planted errors are the kinds I thought of. The receipt-side breaches depend on how often they occur in CORD. And the judge is a model: that's why there is a human-agreement number.

**Trade-off.** Reported recall is per error *kind*, so a claim with an inflated amount that is caught as "claim exceeds receipt" counts, but one caught only because the receipt was unclear does not. Stricter than "decision was not approve", and more honest about what the checks actually detect.

**What the test run showed about extraction (final numbers in `results/metrics.json`).** Haiku 5.5 and Opus 5.5 reached the same item F1 (0.92) and the same accuracy on totals (97%). Opus cost about 30 times more per receipt and was slightly slower. The one real difference: Opus called 93 receipts "clear" against Haiku's 75, so a Haiku deployment sends more clean claims to a human. Most of the item errors on both models are the same label disagreements seen in Phase 2: zero-priced bundle lines the model lists and CORD omits, a trailing "1" folded into an item name, and a "Sub Total" that CORD calls the total. The rest are real slips: one quantity left blank although the raw line starts with "2", one blurry "Tetes" read as "Tefes", a unit price copied from the line-total column, and one tax line missed.

**A bug found on the test split, and how it was handled.** The first 17 test claims showed clean claims being held because their item lines summed to the pre-tax subtotal while the claimed amount was the receipt total including tax. That is a bug in the claim-lines check (the validation sample had no clean claim with tax, so it never showed). The run was stopped, the check fixed to accept lines that equal the receipt subtotal or the amount less the receipt's tax and service, two tests added, and the run restarted from scratch. The partial first run is kept in `results/checks_test_run1_partial.log`. Fixing a code bug is different from tuning a prompt to the test set, but it still has to be disclosed, so it is.

**Interview answer: small model vs large model, which would you deploy?** Haiku. On this task it reads receipts as accurately as Opus at a thirtieth of the cost, and the pipeline is designed so that reading is the *only* job the model has to do well; arithmetic, policy lookup and evidence checking are code. The price of Haiku is more "partly unclear" calls, which cost a human a glance. If that review load mattered more than API cost, I'd try Opus only on receipts Haiku marks unclear, which is a routing rule, not a model swap.

**What the test run showed about the checks (from `results/checks_test_claude-haiku-5-5.json`).** 47 of 50 planted errors were caught by an issue of the matching kind: inflated amounts 10/10, extra items 10/10, claim lines not summing 10/10, policy breaches 9/10, wrong quantities 8/10 (the two misses were still rejected, just under the "claim exceeds receipt" label). Decision accuracy was 81 of 100. Of 41 clean claims, 10 were flagged with an issue and 5 more held only because the image was partly unclear. The verifier dropped 1 of 56 rule-check issues. Natural breaches were weaker: the 500k two-approver threshold was raised on 1 of 3 claims and the packaging cap on 0 of 2, which says the rule check pays more attention to line items than to claim-level thresholds. See `results/error_analysis.md` for the five worst cases and why the 24% false-alarm figure is an upper bound.

**Interview answer: what's your worst failure case, and why does it happen?** A clean claim rejected because the member wrote `SATE ATI GO` and the receipt printed `SATECATIGO`. The fuzzy name matcher relies on word boundaries, the receipt had none, the score fell below the threshold, and a deterministic check raised a high-severity "item not on receipt". The lesson cuts both ways: deterministic code is predictable and cheap, but a rule written for tidy input fails on messy input just as confidently. The fix is one line (also compare with spaces removed), and it is the first thing on the next-steps list.

**What the judge found on 100 test drafts (from `results/drafts_test_claude-haiku-5-5.json`).** Means out of 5: accuracy 4.55, evidence 4.90, clarity 4.71, tone 4.95; 5 of 100 drafts scored below 4 on accuracy. The five all share one slip: when the arithmetic check reported "claim lines sum to X but the amount is Y (receipt tax + service = Z)", the writer sometimes told the member that the difference "matches" the tax and service when the numbers did not actually agree. The draft model was adding a sum of its own instead of repeating the one it was given. That is exactly the failure the design tries to keep out of the LLM steps, and it crept back in through prose. Fix for next time: have the maths check state the comparison in words ("the gap of 11,000 is not explained by tax and service of 10,091") so the writer has nothing left to compute.

**Interview answer: how do you know the drafts are good?** Two ways. A larger model scores every draft against a written rubric with the same facts the writer had, and ten drafts are scored by a person so the judge itself is checked. The judge's low scores were useful: they pointed at a concrete writer slip, which is the point of measuring instead of eyeballing.


## Phase 7: MCP server

**What we built.** `src/receipted/mcp_server.py` exposes one tool, `check_document(image_path, amount, submitter, purpose, items, …)`, over the Model Context Protocol using the official `mcp` Python SDK (v2, class `MCPServer`). It wraps `run_claim()` and returns a compact result: decision, reason, verified issues with evidence, dropped count, draft, cost and time. `scripts/mcp_client_test.py` spawns the server over stdio exactly as Claude Desktop does, lists the tools and calls the tool on a sample claim.

**What MCP is, in one paragraph.** A standard way for an AI app (the client, e.g. Claude Desktop) to discover and call tools that someone else wrote (the server). The server describes each tool with a name, a description and a JSON schema for its inputs; the client's model reads those and decides when to call it; the call and the result travel as JSON messages over a pipe (stdio) or HTTP. The point is that the tool is written once and any MCP client can use it, instead of every app needing its own integration.

**Why this design.** The server is a thin wrapper: no logic lives in it, so the CLI, the Streamlit app and the MCP tool all run the same graph and give the same answer. The tool returns a small, flat result rather than the full state because the calling model has to read it and reason about it; retrieval and trace blobs would only waste its context. Numbers arrive as JSON floats, so the wrapper converts whole numbers back to ints.

**Likely interview questions.**
- *What does the model on the other end actually see?* The tool's name, its docstring and the input schema that the SDK derives from the Python type hints. That text is the whole "API documentation" the model gets, which is why the docstring says what the tool returns and what `items` should look like.
- *How did you test it?* Not by calling the Python function. The test script starts the server as a subprocess and talks the real protocol: initialise, list tools, call tool, parse the structured result. If the schema or transport were wrong, the test would fail even though the function works.

**Trade-off.** stdio only. It is what Claude Desktop uses and needs no network or auth. Serving it over HTTP for other clients would need the SDK's streamable-http transport plus authentication, which is a separate piece of work.


## Phase 8: After comparing with similar projects

**What we built.** Three fixes from the error analysis (space-insensitive name matching, a name-similarity guard for price-list issues in the verifier, a deterministic empty-purpose check), then a second test run reported beside the first; `src/receipted/duplicates.py` (duplicate-receipt detection, clause C9); `eval/hallucination_probe.py` (mask the printed total, check the model abstains); `eval/stats.py` (bootstrap confidence intervals, now on every headline number); `eval/compare.py` (a regression gate between two runs).

**Why a second test run, and why both are shown.** The fixes came from failures seen on the test split, so a re-run is not a fresh measurement: I knew what to fix because the test set told me. Showing run 1 and run 2 together is the honest version. The effect was 47→48 planted errors caught, 81→83% decisions right, 10→8 false alarms on clean claims, and the verifier now drops 4 wrong-product price matches instead of 1. Small, in the right direction, and the intervals (recall 90–100%, decision accuracy 76–90%) say how much of that could be noise.

**Why confidence intervals.** With 100 claims, "96%" sounds precise and is not. Resampling the claims with replacement 4,000 times and taking the middle 95% of recomputed results gives the range a different 100 receipts might produce. None of the similar GitHub projects report this; one (docparse-vlm) planned to. It is the cheapest way to look like you understand measurement, because you do.

**Why a hallucination probe.** The whole design rests on "no evidence, no flag". The extraction step is the one place a number can appear from nowhere. Painting over the real total and asking again tests exactly that: 9 of 10 abstained, and the tenth read a second printed copy of the same amount, which is the right answer. Ten receipts is a small probe; the script scales to the whole split for a few cents.

**Why duplicates are deterministic.** A duplicate is a fact about history (this receipt was claimed before), not a judgement, so it lives in code with a registry file. Two signals: identical image fingerprint (same photo) and same total plus 80% of item names (a new photo of the same paper). Rejected claims are not registered, otherwise a corrected resubmission would be flagged as a duplicate of its own rejection.

**Likely interview questions.**
- *You changed the system after seeing test results. Isn't that cheating?* It would be if I reported only the second run as if it were the first. I report both, say why the fixes were made, and give intervals. A bug fix found on test is normal engineering; hiding the first number is the problem.
- *How do you know the model doesn't make up totals?* I removed the total from real receipts and asked again. It said "not printed" 9 times out of 10, and the tenth time it found the amount printed elsewhere on the same receipt.

**Trade-off.** The duplicate registry is a local JSON file, fine for one treasurer on one laptop; a club with several approvers would need it in a shared store. The probe masks only the total; masking item prices and the subtotal is the natural extension.
